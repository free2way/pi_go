# 18 · PiGO Node 设计（本地节点 / 最小权限访问用户项目目录）

> **状态：设计草案，未实现。** 本文不含任何已落地代码；文中出现的路由、表结构与命令行均为**建议**，未在仓库中实现。文末「现状证据」一节列出的才是当前已存在的实现，用于说明新设计如何复用既有概念。
>
> 约束回顾：本轮不允许改动 `src/worker`；因此本设计只描述边界与契约，不涉及对 worker 的修改。

## 0. 目标

让**服务端**能够安全地操作用户**本地机器上的项目目录**，且遵循最小权限：

- 用户不必把项目搬到服务器、也不暴露入站端口；
- 服务端默认**看不到**任何本地目录，必须由用户在本地对**具体目录**显式授权；
- 读写分离：只读（浏览 / 导出 diff）与读写（执行任务、写回工作区）是两种可分别授予的能力；
- 执行受命令白名单与沙箱约束，资源（Token / 成本 / 时长 / 并行）可被运行预算硬性截断。

非目标（本设计明确排除）：把 PiGO Node 变成一个通用远程控制代理；允许服务端在未配对、未授权、被吊销的节点上执行任意命令。

## 2. 提议架构

### 2.1 组件

```
┌──────────────────────── 服务端（Fastify + Postgres） ────────────────────────┐
│  /api/nodes/pair  /api/nodes/heartbeat  /api/nodes/jobs（出站队列）           │
│  Node Registry（节点、令牌指纹、授权目录、范围、吊销）                          │
└───────────────▲───────────────────────────────────────────────┬──────────────┘
                │ 出站 WSS/HTTPS（节点发起，服务端只应答）           │ 任务/结果
┌───────────────┴───────────────────────────────────────────────▼──────────────┐
│  PiGO Node（用户机器上的本地 daemon）                                          │
│  - 目录 opt-in 注册表（本地 → 仅本地可见）                                      │
│  - 只读 / 读写范围；命令白名单；资源上限                                        │
│  - 本地沙箱执行（复用现有容器/进程隔离思路）                                    │
│  - 本地审计日志                                                                │
└───────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 关键约定（建议）

- **仅出站连接**：PiGO Node 启动后主动向服务端建立长连接（WebSocket over TLS）或轮询；**节点不监听任何入站端口**，家庭/公司网络无需端口映射。
- **设备配对**：用户在服务端生成一次性配对码（短时效），在本地 `pigo-node pair <code>` 输入，完成双向验证后节点获得长期节点身份（`nodeId`）与令牌。
- **每节点令牌 + 设备绑定**：令牌仅存于本地安全存储（见 §9 开放决策），服务端只存**令牌哈希/指纹**，不存明文。
- **逐目录显式 opt-in**：用户在本地执行 `pigo-node allow <绝对路径> --scope read|write`；服务端**不能**自行新增目录授权。取消授权即撤销。
- **范围最小化**：`read` = 允许目录列举、文件读取、diff 生成；`write` = 额外允许在**本次运行的工作副本**内写入（不在用户原始目录内直接改）。
- **命令白名单**：节点只执行白名单内的检查命令（沿用工作区 `defaultChecks` 与 owner 显式配置），白名单外一律拒绝并记录。
- **沙箱执行**：任务的执行发生在一次性、可销毁的工作副本中（对应现有 run worktree 概念），原始目录默认只读挂载；资源上限由预算强制（`src/worker/budget.ts`）。

### 2.3 与「工作副本」的关系

沿用现有模型的直觉：**用户目录是源，运行目录是副本**。节点在本地为每次运行创建 worktree/副本（如 `<cache>/pigo/runs/<runId>`），任务在副本里推进；`read` 范围只把源目录用于读取与 diff；`write` 范围允许把已验收的补丁**显式合并回**源目录（需该目录被授予 `write` 且本运行被显式同意，见 M2）。这与服务端侧 `<PI_WORKSPACE_ROOT>/runs` 的语义一致，只是物化位置从服务器换到用户机器。

## 3. 传输方案对比

| 维度 | A. 出站 WebSocket (WSS) | B. 出站 HTTPS 长轮询 | C. SSH（服务端 → 用户机器） |
| --- | --- | --- | --- |
| 连接方向 | 节点 → 服务端（唯一） | 节点 → 服务端（唯一） | 服务端 → 用户机器（**入站**） |
| 实时性 | 最好（双向复用一条连接） | 中等（受轮询间隔/挂起时长影响） | 好 |
| 网络要求 | 只要求出站 443 | 只要求出站 443（可过纯 HTTP 代理） | 需开放/穿透 SSH，NAT 下需反向隧道 |
| 代理友好度 | 一般（部分代理不懂 Upgrade） | 最好 | 差异大 |
| 实现复杂度 | 中（心跳、重连、背压） | 低（无连接状态） | 中（密钥分发、堡垒机、审计复杂） |
| 安全面 | 令牌 + TLS；服务端不可主动连入 | 同 A，且天然无长连接状态 | 需管理 SSH 密钥/known_hosts；暴露入站面 |
| 断线期间 | 队列在服务端，上线补投 | 同 A | 受连接可用性影响 |
| 建议 | **默认方案**（M1 起） | 备选（受限网络/仅需只读） | 不作为默认；仅在企业已有 SSH 运维体系时作为可选后端 |

选择理由：A/B 都满足「无入站端口、逐目录 opt-in、令牌可吊销」；C 引入入站监听与 SSH 密钥运维，与最小权限目标相悖，仅保留为企业可选集成。**关键点：无论 A/B/C，授权判定、命令白名单、沙箱与审计都在节点侧执行，服务端不能绕过。**

## 4. 威胁模型

假设服务端可能被攻破、令牌可能泄露、用户目录内容可能恶意、网络可被中间人观察。逐项给出缓解与残余风险。

| # | 威胁 | 场景 | 缓解 | 残余风险（需运维/监控） |
| --- | --- | --- | --- | --- |
| T1 | **伪造服务端** | 攻击者伪装服务端骗取节点执行 | 节点固定服务端证书/公钥指纹（pin），配对时人工核对短码；TLS 校验不可关闭 | 用户主动信任了错误指纹 |
| T2 | **窃取节点令牌** | 令牌从本地或备份泄露 | 令牌仅存 OS 安全存储、服务端只存指纹；令牌绑定节点公钥（挑战-应答），单用令牌不能冒充；可即时吊销 | 令牌 + 本机私钥同时被窃 |
| T3 | **已吊销节点重连** | 被吊销设备尝试恢复 | 服务端权威吊销列表；吊销后拒绝配对与心跳，节点收到 `revoked` 立即清除本地令牌并停用目录授权 | 离线节点在联网前仍可在本地执行（但无法上报/同步） |
| T4 | **恶意项目内容** | 仓库脚本/构建钩子在执行克隆或检查时作恶 | 命令白名单；沙箱内执行、默认断网（对应 `network: none`）；不自动执行仓库钩子（如 git hooks）；插件默认关闭（对应 `plugin-policy` 默认 off + sha256 pin） | 白名单内的命令若有漏洞仍可能造成影响（如已知 CVE） |
| T5 | **路径穿越** | 请求携带 `../../etc/passwd` | 复用 `resolveInsideRoot` 语义：拒绝 `..`/绝对路径（`src/worker/workspace-paths.ts:41-52`）；所有路径先 `realpath` 归一化 | 无（若实现严格） |
| T6 | **符号链接逃逸** | 目录内软链指向授权范围之外 | 解析真实路径后校验仍在允许根内；跨边界的软链一律拒绝 | 允许根本身被替换（需文件监视/重新校验） |
| T7 | **资源滥用** | 挖矿、巨大仓库、无限输出 | 预算硬截断（Token/成本/调用/时长，`src/worker/budget.ts`）；CPU/内存/PID/磁盘上限；输出截断 | 上限内仍可能占满用户机器（需可观测与可中断） |
| T8 | **数据外泄** | 只读范围被用来批量拉取私密文件 | `read` 仅对**显式 opt-in 的目录**生效；服务端请求越界即拒绝并审计；可对单目录设上限（文件数/字节） | 授权目录内的敏感文件会被读到（授权即知情） |
| T9 | **中间人 / 重放** | 拦截任务或结果 | 全链路 TLS；每条任务带 `nonce`/`expiry`/`runId`，节点校验时限与绑定；结果签名 | 服务端已被攻破时不可防 |
| T10 | **供应链** | 恶意 Node 二进制更新 | 更新包签名校验；不允许静默降级；更新通道可关闭（见 §9） | 用户在本机安装被篡改的发行版 |

设计原则：**fail-closed**——任何校验失败（路径、白名单、范围、令牌、时间戳）都拒绝执行并写审计，而不是降级放行。

## 5. 映射到既有概念

| 既有概念 | PiGO Node 中的延续 | 备注 |
| --- | --- | --- |
| `Workspace` / `nodeId`（默认 `'server'`） | 新增 `nodeId = <本地节点>` 的工作区；注册来源从「服务端相对路径」变为「节点上报的本地目录」 | `nodeId` 字段已存在（`src/shared/types.ts:639`），无需新表即可扩展语义 |

| 产物 / 补丁导出 | M1 即支持：节点生成 diff、上传为 artifact；服务端沿用 `/api/runs/:id/artifacts|/patch` | `src/server/artifact-api.ts`、`src/server/run-patch.ts` |
| 插件 / 技能允许列表 | M3：节点侧白名单 + sha256 pin；服务端只下发允许项，不改本地策略 | 对应 `src/worker/plugin-policy.ts` |

## 6. 分阶段实现计划

> 每阶段都必须能单独上线、单独回滚，且默认关闭（feature flag）。

### M1 — 只读浏览 + diff 导出（默认关闭）

- 交付：出站 WSS 通道、设备配对、节点令牌、逐目录 `read` opt-in、目录列举/文件读取、运行时生成 diff 并上传 artifact。
- 服务端能力：把「用户本地目录」注册为 `read` 工作区；只读路由全部生效；写路由对本地节点工作区返回 `WORKSPACE_READ_ONLY`。
- 风险最低：不改用户原目录，只读+上传。
- 验收要点：无入站端口、越界路径被拒、吊销即时生效、断线补投。

### M2 — 读写 + 每次运行显式同意

- 交付：`write` 范围；每次运行前在节点本地弹出生效的**逐次同意**（同意范围=本次运行、本次副本），运行结束后可选择性写回源目录（默认不写回）。
- 服务端：`write` 授权、合并/写回动作仍受管理员与 `WORKSPACE_READ_ONLY` 规则约束。
- 验收要点：未同意不得写；同意可撤销；写回可审计、可回滚。

### M3 — 插件 / 技能同步

- 交付：服务端下发允许的扩展/技能/提示模板清单（带 sha256 pin），节点本地按白名单加载；未 pin 的按策略拒绝。
- 验收要点：清单变更可审计；本地策略优先，服务端不能强制加载未允许项。

## 7. 运维要求

- **卸载**：`pigo-node uninstall` 必须①移除本地令牌与私钥；②清理运行副本缓存；③向服务端注销节点；④在服务端记录一条审计事件。卸载后残留目录授权一律失效。
- **密钥/令牌轮换**：支持无损轮换（新令牌生效→旧令牌吊销），节点定期自动轮换；服务端保留指纹历史用于审计。
- **双侧审计日志**：
  - 节点侧：配对/授权/授权撤销/每次任务（命令、范围、路径、结果、审批）本地落盘，用户可导出；
  - 服务端侧：节点上线/离线、任务下发、artifact 接收、吊销、轮换；
  - 两侧以 `runId`/`nodeId`/`nonce` 对账，冲突时以**节点侧本地日志**为准（因为执行发生在本地）。
- **可观测性**：节点心跳含版本、已授权目录数、最近错误；异常（白名单拒绝、越界、资源触顶）上报为告警。

## 8. 开放决策（尚未拍板）

| 决策 | 选项 | 取舍 |
| --- | --- | --- |
| 令牌存储 | OS 钥匙串（Keychain/DPAPI/libsecret） vs 加密文件 | 钥匙串更安全但跨平台实现/自动化测试更难；加密文件便于无头部署 |
| 更新通道 | 自动静默 / 提示后手动 / 可关闭 | 安全补丁需要及时性，但静默更新是供应链攻击面 |
| 多设备 | 一账号多节点 vs 一节点多账号 | 影响授权模型与审计对账（建议先支持一账号多节点，目录授权按节点隔离） |
| 传输后端 | 默认 WSS；是否提供 SSH 后端 | SSH 便于企业既有运维，但引入入站与密钥管理（见 §3） |
| 网络受限场景 | 长轮询回退是否 M1 就需要 | 增加实现面，但对代理严格的网络更友好 |

## 9. 明确不做的事（本设计边界）

- 不允许服务端在未配对/未授权/已吊销的节点上执行任何命令；
- 不允许服务端指定任意本地绝对路径（只能选用节点已 opt-in 的目录）；
- 不允许默认写回用户源目录（写回需逐次同意 + `write` 授权）；
- 不把节点私钥/令牌写入仓库、日志或明文配置。

## 10. 结论

设计可行且与现有概念（`nodeId`、`read|write` 授权、run worktree、sandbox、插件白名单、artifact/patch 导出）高度同构；核心新增量是「出站通道 + 设备配对 + 逐目录 opt-in + 双侧审计」。**本文为设计草案，仓库中尚无对应实现。**
